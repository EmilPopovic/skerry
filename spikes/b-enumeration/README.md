# Spike B — enumeration throughput

**Status:** run and recorded. Verdict below. Cold cache is owed and the
commands to run it are at the end.

## Question

What does `getdents64` plus batched `statx` on a job pool actually buy over
`std::fs::read_dir` at a million files, and can a mount that stops responding be
kept off the UI thread?

## Bar

Quoted from [08-roadmap.md](../../docs/08-roadmap.md#phase-0--five-spikes-34-weeks),
written before the first line of code and not adjusted afterwards:

> **Bar:** warm-cache full walk under 1 s · first 200 visible rows on screen
> within 30 ms of opening any directory · a hung mount never blocks the UI
> thread.

Three conditions. The verdict is the conjunction.

## What it decides

[04-architecture.md](../../docs/04-architecture.md#data-layout) already asserts
the answer — "`read_dir`'s per-entry allocation and implicit stat is a measurable
tax at a million entries" — and then says, in the same paragraph, that **Spike B
exists to quantify it before we commit.** This spike either produces that number
or removes a line from the architecture document.

The third condition is rule 1's canonical test in
[03-principles.md](../../docs/03-principles.md), stated there as "any frame
exceeds 8 ms while an sshfs mount is unplugged mid-listing". Spike A established
that the renderer can hold 8 ms. This is where we find out whether the
*filesystem* can be kept away from it.

## Method

### Machine

The same machine as [Spike A](../a-million-rows/README.md#machine), and the same
caveat: a 24-thread 2024 laptop, **not** the "2021-era four-core laptop" the
budgets are written against. It is a worse mismatch here than for Spike A,
because thread count directly sets the job pool's width. The reference-machine
run is owed.

Enumeration is also load-sensitive for the same reason Spike A's llvmpipe arm
was, so the sweep waits for a one-minute load average under 1.3 and records the
load beside every sample.

### The tree

Generated by this spike, seeded, so it is reproducible rather than whatever
happened to be on the disk. 1,000,000 empty files — the measurement is metadata
throughput, and file contents would only add page-cache noise.

Shape matters more than size. A real tree is mostly small directories with a few
enormous ones, and the 30 ms condition is decided by the enormous ones:

| Directories | Entries each | Files |
| --- | --- | --- |
| 1 | 100,000 | 100,000 |
| 10 | 10,000 | 100,000 |
| 100 | 1,000 | 100,000 |
| 7,000 | 100 | 700,000 |

Nested to depth 5. Filenames come from Spike A's generator, so the mix of ASCII,
CJK, RTL, emoji and 120-character names is the same in both spikes and name
length is realistic rather than uniform.

It lives at `/var/tmp/skerry-spike-b`, on ext4. **Not `/tmp`:** the tmpfs there
has 1,048,576 inodes in total, and a million files would consume 95% of them.

### The four arms

Each walks the same warm tree in the same process, and produces the same thing: a
columnar store of names, sizes, mtimes and flags.

| Arm | What it does | What it is |
| --- | --- | --- |
| `read_dir` | `std::fs::read_dir`, names only | the floor, and what a listing needs at minimum |
| `read_dir+meta` | plus `entry.metadata()` per entry | what a file manager actually needs, by the ergonomic route |
| `getdents64` | `rustix::fs::RawDir`, names and `d_type` | no stat at all — `d_type` gives file-versus-directory free |
| `getdents64+statx` | plus `statx` batched onto the job pool | the design in 04-architecture |

The comparison that matters is `read_dir+meta` against `getdents64+statx`, because
those two produce the same columns. `read_dir` and `getdents64` are the floors
each is built on, measured so the tax can be attributed to the right half.

### The job pool

Written here, not imported. [ADR 0005](../../docs/adr/0005-no-async-runtime.md)
allows one pool for the process and no async runtime, so this is `std::thread`
plus a channel plus a cancellation flag, sized `ncpu - 2`. Using `rayon` to
measure a design that forbids `rayon` would measure nothing.

### Time to first 200 rows

The 30 ms condition is not about the full walk. It is about how long after
opening a directory the user sees the top of it, so it is measured as **time from
the open call until 200 entries are in the store**, on directories of 1,000,
10,000 and 100,000 entries. The 100,000-entry directory is the binding case.

Rows are shown as soon as their names exist; `statx` columns fill in behind them.
That is not a measurement trick, it is the progressive streaming rule 1 requires,
and the number is meaningless unless the arms are held to it equally — so
`read_dir+meta`, which cannot separate the two, is measured with its stat cost
included and that is the point.

### The hung mount

An unprivileged FUSE filesystem, mounted by this spike, whose `readdir` and
`lookup` sleep for 60 seconds. That is a faithful stand-in for sshfs to a host
that has stopped answering, and unlike sshfs it is controllable, needs no network
and no root.

The test: start a frame loop that does Spike A's work at 8 ms, begin a walk of the
hung mount on the job pool mid-listing, and record every frame interval until the
walk is cancelled.

> **Pass:** no frame exceeds 8 ms, the walk is cancellable, and the UI thread
> issues zero filesystem syscalls throughout — the last asserted by construction,
> because the frame loop has no path to one.

### What is measured

| Number | How |
| --- | --- |
| Full walk | Wall clock, warm cache, 3 repeats, min/median/max, files per second |
| Time to first 200 rows | Wall clock from `open` to the 200th name in the store |
| Frame time during a hung mount | Frame interval on the simulated UI thread, p99 and max |
| Peak RSS | `VmHWM`, as a proxy for the per-entry allocation tax |
| `statx` calls | Counted, so the batching can be shown to have happened |

### Cold cache, not run

The roadmap asks for cold cache as well as warm. Dropping the page cache needs
`echo 3 > /proc/sys/vm/drop_caches` as root, and this machine has no passwordless
sudo, so **the cold-cache arm is owed and is recorded as owed rather than
estimated.** The exact commands to run it are at the end of this document.

Cold cache changes what is being measured: a warm walk measures our code, a cold
walk measures the storage device and the kernel's readahead, with our code as a
rounding error. Both matter — the warm number is the one the architecture claims
and the cold number is the one a user feels on the first open after boot.

## Result

Warm cache, 1,000,000 files, three repeats per arm, machine idle at load 1.28.
Raw output in [runs/](runs/).

### Full recursive walk, seconds

| Arm | min | med | max | files/s | stat calls | peak RSS |
| --- | --- | --- | --- | --- | --- | --- |
| `read_dir` | 0.309 | **0.314** | 0.542 | 3,248,859 | none | 82.1 MB |
| `read_dir+meta` | 1.149 | **1.195** | 1.204 | 854,367 | 1,021,338 | 82.2 MB |
| `getdents64` | 0.263 | **0.263** | 0.264 | 3,882,945 | none | 82.7 MB |
| `getdents64+statx` | 0.526 | **0.530** | 0.537 | 1,927,700 | 1,000,001 | 84.5 MB |

**The comparable pair is the second row against the fourth**, because those are
the two that fill the size and mtime columns. `getdents64+statx` is **2.25×
faster**, and that factor is the difference between missing the bar and meeting
it: 1.195 s against a 1 s bar, versus 0.530 s.

The line in
[04-architecture.md](../../docs/04-architecture.md#data-layout) that this spike
was created to test — "`read_dir`'s per-entry allocation and implicit stat is a
measurable tax at a million entries" — is confirmed, with one correction. Taking
the two halves separately:

- **The implicit stat is almost all of it.** `read_dir` to `read_dir+meta` costs
  0.881 s; `getdents64` to `getdents64+statx` costs 0.267 s. The same million
  `statx` calls, 3.3× cheaper when batched onto the pool instead of issued
  inline from the walking thread.
- **`d_type` removes 21,337 stat calls outright.** `read_dir+meta` makes
  1,021,338 of them and `getdents64+statx` makes 1,000,001 — the difference is
  exactly the directories, which `getdents64` types for free.
- **The per-entry allocation is *not* a memory tax.** Peak RSS is 82.1 MB for
  `read_dir` and 84.5 MB for `getdents64+statx` — flat across all four arms, and
  dominated by the store's 60 MB. `read_dir`'s `PathBuf` and `DirEntry` per entry
  are churn, not retention: the allocator hands the same pages back. The tax is
  real and it is **CPU time**, not footprint. The architecture document says
  "allocation and implicit stat" as though both were costs of the same kind; the
  measurement says one is CPU and the other is nothing.

`read_dir` versus `getdents64` with no stat at all is 0.314 s against 0.263 s —
a 19% floor difference that is the allocation churn on its own, and the smallest
number in this table. **Nearly all of the win is in deferring `statx`, not in
avoiding `read_dir`.** That ordering matters: it says the important thing to get
right in `sk-fs` is the batching, and `getdents64` is the smaller half of the
decision.

### Time to first 200 rows, milliseconds

| Arm | 100,000-entry | 10,000-entry | 1,000-entry | 100-entry |
| --- | --- | --- | --- | --- |
| `read_dir` | 0.092 | 0.087 | 0.089 | 0.018 |
| `read_dir+meta` | 0.143 | 0.132 | 0.134 | 0.042 |
| `getdents64` | 0.081 | 0.077 | 0.078 | 0.014 |
| `getdents64+statx` | 0.081 | 0.076 | 0.083 | 0.014 |

Against a 30 ms bar, the worst cell is **0.143 ms — 210× under it**, and the
directory size barely registers because one 32 KiB `getdents64` buffer already
holds far more than 200 entries. The 100-entry column reports the whole
directory, since 200 rows cannot come out of 100 files.

This condition is met so easily on a warm cache that it is **not a meaningful
test until the cold-cache arm runs.** Warm, it measures a memcpy out of the
dentry cache. Cold, it measures a disk, and that is the number a user feels on
the first open after boot. Recorded as a pass, flagged as an easy one.

### Hung mount — rule 1's canonical test

| Where the listing runs | p50 | max |
| --- | --- | --- |
| On the job pool, frame loop measured | 4.000 ms | **4.001 ms** |
| On the frame loop itself | — | **28,000 ms** |

**PASS**, and the second row is why the first one means something.

The frame loop held 4 ms while a walk of a dead mount was in flight on the pool,
and the filesystem confirms it was genuinely entered: 4 requests reached it and
none were answered. Then the same listing, issued from the frame loop instead,
blocked it for **28.0 seconds — 3,500× the 8 ms budget.** Same mount, same
syscall, same process; the only variable is which thread made the call.

The 28 seconds is four of the filesystem's ten-second stalls, minus what had
already elapsed: a dead mount serialises on one request at a time, so the
control also waited behind the requests the pool arm left outstanding. That is
what makes a hung mount worse than a slow one — the queue is unbounded and every
later caller inherits it.

Without the control arm this condition could only ever pass, because a frame loop
with no path to a filesystem syscall cannot be blocked by one. "No frame exceeded
8 ms" would have been a restatement of the design rather than a measurement of
it.

## Verdict

**Go, with the cold-cache arm owed.**

| Condition | Result |
| --- | --- |
| Warm-cache full walk under 1 s | **PASS** at 0.530 s — and `read_dir+meta` **misses** at 1.195 s |
| First 200 rows within 30 ms | **PASS** at 0.143 ms worst case, on a warm cache only |
| A hung mount never blocks the UI thread | **PASS** at 4.001 ms, against 28,000 ms for the same call on the frame loop |

`getdents64` plus batched `statx` earns its place, and the number that justifies
it is 2.25× on the comparable pair — enough to move the design from missing the
bar to meeting it with room. It is worth being precise about where the 2.25×
comes from, because the architecture document is not: **the batching is the win,
`getdents64` is the trim.** Deferring `statx` to the pool accounts for 0.614 s of
the 0.665 s difference; replacing `read_dir` with `getdents64` accounts for
0.051 s.

Three things this spike does **not** license:

1. **Cold cache is unmeasured**, and it is the arm that decides whether the
   30 ms condition is real. Everything above is a measurement of the dentry
   cache and of our own code; cold, the storage device dominates and our code
   becomes a rounding error. Commands below.
2. **One filesystem, one device.** ext4 on NVMe. The roadmap's matrix — btrfs,
   xfs, NFS — belongs to [Spike E](../../docs/08-roadmap.md#spike-e--operation-engine-correctness),
   but enumeration on a network mount is a different shape of problem from
   enumeration on a local one, and this spike did not touch it. The hung-mount
   arm is a stand-in for sshfs, not a measurement of sshfs.
3. **22 pool workers.** The reference machine has four cores and would run two.
   The batching win is a parallelism win, so it is the number in this spike most
   likely to shrink on the machine the budgets are written against. That makes
   the reference-machine run more important here than it was for Spike A, not
   less.

What lands as a permanent gate: the four-arm comparison as a regression test on
the enumeration path, and the hung-mount test **with its control arm**, which
belongs in CI as rule 1's executable form.

## Running the cold-cache arm

Not run here: dropping the page cache needs root, and this machine has no
passwordless sudo. It is one command, and the numbers above are what it should be
compared against.

Between **every** measurement, because a walk warms what the next walk reads:

```sh
sync
echo 3 | sudo tee /proc/sys/vm/drop_caches > /dev/null
```

`3` drops the page cache, the dentry cache and the inode cache. `1` drops only
the page cache and leaves the dentries, which is the one that matters for
enumeration — so `3` is the honest choice and `1` would flatter us.

Then, one arm per drop:

```sh
cd spikes/b-enumeration
for arm in read_dir read_dir+meta getdents64 getdents64+statx; do
    sync; echo 3 | sudo tee /proc/sys/vm/drop_caches > /dev/null
    ./target/release/spike-b-enumeration --only "$arm" --repeats 1 --skip-hang
done
```

`--repeats 1` is not a shortcut: the second repeat of a cold run is a warm run,
so a cold measurement has exactly one sample per drop. Three cold samples means
three drops.

The harness will print its usual warming pass first and that pass **is** the cold
measurement, which the current code discards as warm-up. Read the `warming` line
rather than the table, or add a `--cold` flag that skips the warming walk — the
second is better and is left undone rather than done untested.

What to expect: the arms should converge, because a cold walk is dominated by the
device and the kernel's readahead rather than by our syscall choice. **If they do
not converge — if `getdents64+statx` stays meaningfully ahead cold — that is a
larger result than anything above**, because it would mean the win survives the
case a user actually notices.

## Reproducing it

```sh
cd spikes/b-enumeration

# Once: writes 1,000,000 files under /var/tmp/skerry-spike-b (about 40 MB and
# 1M inodes, roughly 5 seconds).
cargo run --release -- --generate

# Everything, three repeats per arm.
cargo run --release -- --repeats 3

# One arm, with a peak-RSS figure that means something.
cargo run --release -- --only getdents64+statx --repeats 3 --skip-hang

# The hung mount on its own.
cargo run --release -- --only getdents64 --repeats 1
```

Remove the tree with `rm -rf /var/tmp/skerry-spike-b`.

**The machine must be quiet.** The sweep here waited for a one-minute load
average under 1.3 and recorded the load in every run; Spike A's numbers were
distorted by 6× when its sweep overlapped a `cargo build`, and enumeration is
just as load-sensitive.

### Two environment constraints, found the hard way

- **The tree cannot live on `/tmp`.** The tmpfs there has 1,048,576 inodes in
  total, and a million files would take 95% of them.
- **The FUSE mount cannot live on `/var/tmp`.** `mount(2)` returns `EPERM` for an
  unprivileged FUSE mount there on this machine, while `~/.cache` is allowed —
  so `--hang-at` defaults to `$HOME/.cache/skerry-spike-b-hung`. Symptom if you
  hit it elsewhere: `fusermount3: mount failed: Permission denied`, with
  `fusermount3` correctly setuid and the mountpoint correctly owned.

The hung mount is a FUSE filesystem whose `readdir` sleeps, not sshfs. It
reproduces the part rule 1 cares about — a `getdents64` that never returns, on a
real mount, in another process — without a network, a second host or root. It
does not reproduce sshfs's reconnection behaviour, and Spike D is where real
network mounts belong.
